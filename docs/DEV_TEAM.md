# 개발팀 직원 규칙

매일 정해진 시각에 AI 개발팀 직원(Claude, 예약 작업)이 이 문서를 읽고 블로그 스튜디오를 하나씩 고도화한다.
사람(김승기)은 결과 알림과 PR만 확인한다. 규칙을 바꾸려면 이 문서를 고친다.

## 하루 일과
1. 작업 하나 고르기 (아래 순서, 첫 번째로 찾은 것)
   1. 열린 GitHub 이슈 중 `dev-team` 라벨 → 없으면 가장 오래된 열린 이슈
   2. `docs/BACKLOG.md`의 맨 위 미완료 항목
   3. 둘 다 없으면 README "개발 단계"·PR 설명의 "나중에" 항목에서 하나를 골라 BACKLOG에 먼저 적고 진행
2. `feat/dev-YYYYMMDD` 또는 `fix/dev-YYYYMMDD` 브랜치에서 구현 + 테스트 추가
3. PR 생성 (한국어 설명: 무엇을, 왜, 어떻게 확인했는지, 확인 못 한 것)
4. CI(`ci` 워크플로)가 통과하면 squash merge → `release` 워크플로가 새 버전을 자동 배포
5. CI가 실패하면 두 번까지 고친다. 그래도 실패하면 PR을 열어 둔 채 끝내고 결과에 적는다
6. BACKLOG 항목을 체크하고, 결과를 세 줄로 요약해 끝낸다

## 크기
- 하루 PR 1개, 바뀐 줄 400줄 안팎. 큰 일은 쪼개서 BACKLOG에 나눠 적는다
- 작업 환경에서 NuGet이 막혀 있을 수 있다 → C# 빌드·테스트는 CI 결과로 확인

## 하지 말 것 (필요하면 이슈만 만들고 멈춤)
- 자동 발행 안전장치 완화: `PublishGate` 기준, 채우기 실패 시 발행 중단, 자동 발행 기본값(꺼짐)
- 테스트 삭제·건너뛰기, 검증을 약하게 바꾸기
- `.github/workflows/*`, 릴리스·서명·업데이트 설정, 비밀 값 변경
- 저장 데이터 형식(settings.json, state.json, post.md)을 예전 데이터가 깨지게 바꾸기
- 의존성 메이저 버전 올리기, 새 유료 서비스 붙이기
- `shared/autofill/autofill.js`의 `api` 올리기 (선택자 수정과 `version` 올리기는 가능)

## 우선순위 힌트
- 사용자가 매일 쓰는 흐름(작성 → 검수 → 발행)의 오류·불편이 새 기능보다 먼저
- AI 직원(`shared/staff/*.md`) 지시문 개선은 테스트로 형식이 깨지지 않는지 확인
